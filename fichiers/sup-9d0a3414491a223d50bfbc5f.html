    Pourquoi l'asynchrone ?

    diapos 64–65

    Lire un fichier, appeler une API, interroger une base : ces opérations durent des millisecondes, parfois des secondes. Si le programme attend sans rien faire, l'interface se fige. L'asynchrone permet de lancer l'opération, de continuer à travailler, et d'être prévenu quand le résultat arrive.

    Synchrone
    Chaque instruction attend la fin de la précédente. Simple à lire, mais tout s'arrête pendant une opération lente.
    Asynchrone
    L'opération lente est lancée, le programme continue, le résultat arrive plus tard sous forme de Future ou de Stream.
    Mono-thread
    Un programme Dart tourne sur un seul fil d'exécution par isolate : il n'y a jamais deux lignes de code exécutées en même temps dans le même isolate.
    Concurrence
    Pour un calcul lourd, on délègue à un autre isolate (un autre fil, sans mémoire partagée) : chapitre 11.

    Interface bloquée ou fluide ?

    Lancez un chargement de 3 secondes
    clics pris en compte : 0
    en attente
    À retenir
    • Dans Flutter, une seule opération synchrone de 300 ms suffit pour que l'animation saccade ; à partir d'une seconde, l'utilisateur pense que l'application a planté.
    • Entrées / sorties (réseau, fichiers, base) : toujours asynchrone. Calcul lourd : un isolate.

    Un programme Dart (un seul isolate) peut-il exécuter deux fonctions en même temps ?

    L'asynchrone n'est pas du parallélisme : le code s'exécute toujours un morceau à la fois, mais il ne reste pas bloqué pendant les attentes.

    La boucle d'événements

    diapo 66

    La boucle d'événements (event loop) est le moteur de l'asynchrone. Elle exécute d'abord tout le code synchrone, puis vide la file des microtâches, puis prend un événement dans la file des événements, et recommence.

    La boucle tourne sous vos yeux

    Suivez les files
    Code synchrone (main)
    File des microtâches
    File des événements
    FileQui y entrePriorité
    MicrotâchesscheduleMicrotask, Future.microtask, la suite d'un await sur un Future déjà terminé, les then d'un Future terminéVidée entièrement avant tout événement
    ÉvénementsFuture(...), Future.delayed, timers, E/S, clics, réponses réseauUn seul à la fois, puis retour aux microtâches
    Piège

    Une boucle infinie de microtâches (une microtâche qui en planifie une autre) bloque la boucle : les événements, dont les clics, ne passent plus jamais.

    Qu'affiche print(1); Future(() => print(2)); Future.microtask(() => print(3)); print(4); ?

    Synchrone d'abord (1, 4), puis les microtâches (3), puis les événements (2).

    Les Futures

    diapo 67

    Un Future<T> est une promesse : « une valeur de type T arrivera plus tard, ou une erreur ». Il est d'abord en attente, puis terminé une seule fois, avec une valeur ou une erreur.

    Cycle de vie d'un Future

    Choisissez le dénouement
    crééen attente…?
    À retenir
    • then reçoit la valeur, catchError l'erreur, whenComplete s'exécute toujours (comme finally).
    • Un Future terminé ne change plus ; un second then reçoit immédiatement la même valeur.
    • Oublier de traiter l'erreur d'un Future = « Unhandled exception » dans la console et, dans Flutter, un écran rouge en mode debug.

    Dans quel ordre s'affichent « Avant », « Après » et « Note : 17 » ?

    then enregistre une fonction à exécuter plus tard ; main continue et affiche « Après » tout de suite.

    async et await

    diapos 68–69

    async marque une fonction qui renvoie un Future ; await met cette fonction en pause (sans bloquer le programme) jusqu'au résultat. Le code se lit comme du synchrone, mais s'exécute en plusieurs morceaux.

    Pièges fréquents
    • Oublier await : var page = telecharger(...) donne un Future<String>, pas une String. L'analyseur avertit (unawaited_futures).
    • await n'est permis que dans une fonction async ; main peut l'être : Future<void> main() async.
    • Un await dans une boucle for rend les itérations séquentielles : voulu pour respecter un ordre, à éviter si elles sont indépendantes.

    Gérer les erreurs asynchrones

    diapo 69

    Avec await, une erreur asynchrone se comporte comme une exception ordinaire : try / catch / finally fonctionnent. Sans await, il faut catchError — ou l'erreur n'est attrapée par personne.

    Qui attrape l'erreur ?

    Choisissez le scénario
    À retenir
    • on Type catch (e) cible un type d'erreur ; catch (e, stack) attrape tout et donne la pile.
    • rethrow relance l'erreur après l'avoir journalisée.
    • Dans Flutter, montrez l'erreur à l'utilisateur (SnackBar, message dans le widget) plutôt que de la laisser remonter.

    f().then(print); où f lève une erreur, sans catchError ni try. Que se passe-t-il ?

    Un Future en erreur sans gestionnaire remonte à la zone d'exécution : message « Unhandled exception » et, en debug Flutter, écran d'erreur.

    async*, yield et await for

    diapo 70

    Pour produire un stream, une fonction async* émet ses valeurs avec yield, une par une, au rythme qu'elle veut. Pour le consommer dans une fonction async, await for attend chaque valeur.

    Le générateur pas à pas

    yield émet, await for reçoit
    async*—
    →
    await for—
    À retenir
    • async* renvoie un Stream, async renvoie un Future, sync* renvoie un Iterable (paresseux, sans attente).
    • Le corps d'un async* ne démarre qu'au premier listen ; il se met en pause si l'abonné fait pause().
    • await for traite les événements l'un après l'autre : un traitement long retarde la lecture des suivants.

    Que renvoie une fonction déclarée Stream<int> f() async* { yield 1; yield 2; } ?

    Un générateur ne s'exécute pas à l'appel : il décrit un flux, démarré par listen ou await for.

    StreamController

    diapo 71

    Quand les événements viennent de votre propre code (un bouton, un capteur, un socket), un StreamController fournit les deux bouts : le sink pour pousser des événements et le stream pour les écouter.

    Pilotez un StreamController

    sink à gauche, stream à droite
    Pièges
    • Un controller non fermé garde ses abonnés en mémoire : dans un State Flutter, appelez close() dans dispose().
    • Après close(), tout add lève « Cannot add event after closing ».
    • Exposez le stream, jamais le controller : les autres classes ne doivent pas pouvoir émettre à votre place.

    Concurrence : les isolates

    complément

    L'asynchrone ne rend pas un calcul plus rapide : un tri de 2 millions d'éléments bloque la boucle d'événements, await ou pas. Pour un vrai travail en parallèle, Dart lance un isolate : un autre fil d'exécution avec sa propre mémoire, qui communique par messages.

    exemple complet

    Un champ de recherche qui interroge une API à chaque frappe : il faut attendre que l'utilisateur fasse une pause (debounce), annuler la requête précédente et ignorer les réponses arrivées dans le désordre. Tout ce supplément réuni en un exemple.

    Tapez, et regardez le debounce travailler

    Bonnes pratiques
    • Nommez les fonctions asynchrones par ce qu'elles font, pas par leur mécanisme ; renvoyez toujours un type précis (Future<List<User>>, jamais Future<dynamic>).
    • Un await par attente réelle ; Future.wait pour les attentes indépendantes.
    • Gérez chaque erreur à l'endroit où vous pouvez réagir (message, réessai), et fermez vos controllers et abonnements dans dispose.
    • Utilisez FutureBuilder / StreamBuilder pour afficher, un gestionnaire d'état (Provider, Riverpod, Bloc) pour partager.
